# Agents.md — ZmeyGorynich

Информация о проекте для будущих сессий (оценка и заметки).

## Что это

**ZmeyGorynich** — интерпретируемый язык программирования с «славянской» тематикой (ключевые слова на русском: `молвить`, `сотвори`, `возверни`, `гойда` как `;`, блоки `ухожу я в пляс` / `закончили пляски`). Назначение — игривый эзотерический/обучающий язык поверх Python.

Реализация на **Python 3** (вопреки последнему коммиту «Переписано на С++» — в рабочей директории только Python-код; C++-версии в дереве нет).

## Архитектура (пайплайн компиляции)

`code (.zg)` → `lexer.tokenize` → токены → `parser.parse` → AST (список `Node`) → `evaluator.evaluate` (выполнение).

### Ключевые файлы (`src/zmeygorynich/`)
- `lexer.py` — регулярный токенайзер. Обрабатывает кириллицу, латиницу, руны, многострочные комментарии (`Голос предков шепчет:` ... `Голос предков внезапно стих...`), `#`-комментарии. Славянские операторы в `SLAVIC_OP`.
- `parser.py` — рекурсивный нисходящий (ручной) парсер. `TYPE_MAP` сопоставляет языковые типы (`цело`, `плывун`, `плывун малый точный` и т.д.) с внутренними хинтами (`число:int`, `decimal:30` ...). Генерирует AST-узлы `Node` (см. `node.py`).
- `node.py` — простой AST-узел (`type/value/children/op/type_hint/line/col/alias`).
- `evaluator.py` — основная логика. `Context` (переменные/типы/функции/родительский scope/call_stack), `evaluate`, `evaluate_expression`, `evaluate_condition`, `call_function`, встроенные функции (`builtins`), проверки типов (`check_type`), работа с `Decimal` для точных чисел.
- `interpreter.py` — CLI-точка входа: `python interpreter.py <file.zg>`. Имеет глобальный `DEBUG = True` (печатает токены и AST!).
- `colored_text.py` — `Color` enum с ANSI-кодами (в `requirements.txt` есть `colorama`, но в коде не используется).
- `test.py` — утилита-проверка поддержки рун в терминале (не относится к языку).

### Типы
`цело`(int), `плывун`(float), `плывун малый точный/великий/звездный` (Decimal prec 30/50/100), `строченька`(str), `двосуть`(bool), списки `список <тип>` / `list:...`.

### Синтаксис (ключевое)
- Присваивание с типом: `x быти цело = 42 гойда`
- Функции: `сотвори имя(арг быти тип) изречет тип ухожу я в пляс ... возверни ... закончили пляски`
- Условия: `аще <cond> то ... [аще ли <cond> то ...] [ино ...]`
- Циклы: `покуда <cond> ...`, фиксированные `дважды`/`трижды`/.../`стожды` (2..100).
- Массивы: `созвать_дружину(размер, значение)` или литерал `[1,2,3]`, доступ `a[i]`, присваивание `a[i] = v`.
- Ввод: `внемли("prompt", var)` / `внемли(var)`.
- Импорт: `прочесть книгу "file.zg" [и осмыслить слова как алиас]` → узел `Import`.
- Встроенные: `молвить`, `глас` (печать с типом/рунами), `созвать_дружину`, `тип_значения`, `строчить_значение`, `имя_аргумента`.

## Как запускать и тестировать

- Запуск программы: `python3 src/zmeygorynich/interpreter.py examples/test.zg` (из корня проекта).
- Тесты: находятся в `tests/`, импортируют `from lexer import tokenize` и `from parser import parse` — значит **запускать нужно из каталога `src/zmeygorynich/`**:
  `cd src/zmeygorynich && python -m pytest ../../tests/ -q`
- Зависимости: `pip install -r requirements.txt` (pytest, colorama).

## Оценка состояния и найденные проблемы

**Критический баг (условия/циклы не работают): [ИСПРАВЛЕНО]**
`evaluate_condition` в `evaluator.py` проверял `if node.type == 'Condition'`, но парсер (`parser.parse_*` → `parse_comparison`) генерирует для условий узлы типа `BinaryOp`, а не `Condition`. Следствие: `if`/`аще` и `while`/`покуда` **всегда** считали условие `False` и тела никогда не выполнялись. Исправлено: `evaluate_condition` теперь принимает `node.type in ('Condition', 'BinaryOp')`. Тесты `test_parser.py` (ожидавшие `Condition`) обновлены под `BinaryOp`. Все 6 тестов проходят.

**Тесты некорректны/не проходят:**
- `tests/test_parser.py::test_parse_if_statement` и `test_parse_while_loop` падают, ожидая `node.children[0].type == 'Condition'`, хотя парсер возвращает `BinaryOp`. Тесты отражают старое (сломанное) поведение — их нужно либо поправить под `BinaryOp`, либо исправить парсер под `Condition` и тогда тесты станут валидным регресс-набором на критический баг.
- Все 6 тестов проходят (после фикса критического бага и обновления ожиданий `BinaryOp`).
- Тесты не запускаются «из коробки» из-за относительных импортов (нужен `cd` в `src/zmeygorynich`).

**Другое:**
- `interpreter.py` по умолчанию `DEBUG = True` → при каждом запуске сыпет токенами/AST. Для нормального использования должно быть `False` (или через флаг/ENV).
- `requirements.txt` содержит `colorama`, но код использует собственные ANSI-коды из `colored_text.py` — лишняя зависимость.
- `evaluator.py` (~538 строк после рефакторинга) содержит взаимно-рекурсивное ядро выполнения (`evaluate_expression` ↔ `call_function` ↔ `evaluate`), которое намеренно оставлено вместе. Ранее гигантское walrus-выражение `глас` переписано в читаемую функцию `_glas` в `zg_builtins.py`.

**Рефакторинг (выполнен): разбиение `evaluator.py` на модули.**
- `config.py` (~11) — `DEBUG`, `debug_print`, глобальная точность `Decimal`.
- `typecheck.py` (~112) — `get_type_name`, `map_type_hint_to_display_name`, `stringify_value`, `check_type`.
- `context.py` (~66) — класс `Context`.
- `zg_builtins.py` (~101) — словарь `builtins` + функция `_glas` (лениво импортирует `evaluate_expression` из `evaluator`, чтобы не было цикла импорта). **Важно:** модуль назван `zg_builtins`, а не `builtins` — иначе конфликт со стандартным модулем Python.
- `evaluator.py` (~556) — ядро: `normalize_operator`, `evaluate_expression`, `evaluate_condition`, `call_function`, `evaluate_import` (модульные функции) + класс `Evaluator` с обработчиками `_eval_<Тип>` для каждого узла AST. Публичный API `Context`, `evaluate` сохранён для `interpreter.py`.

**Рефакторинг (выполнен): parser и evaluator → классы.**
- `parser.py`: монолитная функция `parse()` с вложенными замыканиями преобразована в класс `Parser` (методы `parse_primary`, `parse_expression`, `parse_if`, `parse_while` и т.д.). Семантика возвратов (`Return`/`While`/`If`/`FixedLoop` прерывают выполнение, `Call` накапливает `return_value`) сохранена точно. Модульные `evaluate`/`evaluate_import` — обёртки для совместимости.

## Логические операторы (реализовано)
- `и` (and), `или` (or), `не` (not) добавлены в условия и выражения.
- Грамматика (в `parser.py`): `parse_or` → `parse_and` → `parse_not` → `parse_comparison`. Приоритет: `не` выше `и`, `и` выше `или`. Скобки поддерживаются (`не (x > 0)`).
- Токенизируются как `ID` (кириллица), поэтому лексер не менялся.
- В `evaluator.py`: `normalize_operator` маппит `и`→`and`, `или`→`or`, `не`→`not`; `evaluate_expression` обрабатывает логические `BinaryOp` и унарный `UnaryOp` (`не`); `evaluate_condition` делегирует в `evaluate_expression`.

## Важная особенность грамматики (if/elif/else)
Ветви `аще`/`аще ли`/`ино` образуют ОДИН конструкт `If`. Каждая ветвь закрывается собственным `закончили пляски` (как в `examples/test.zg`). Подряд идущий `аще` сразу после закрытого блока интерпретируется парсером как `аще ли` (elif) того же `If`. Поэтому несколько независимых `аще` нужно разделять другими операторами (например, присваиванием) либо оформлять явно как `аще ли`/`ино`. Это дизайн языка, не баг.

## Заметки для разработки
- Язык чувствителен к пробелам/табам в блоках (использует фигурные «пляски», а не отступы), но `lexer` просто скипает пробелы — вложенность блоков определяется парными `ухожу я в пляс`/`закончили пляски`.
- Руны (ᚠᚢᚦ...) допустимы в идентификаторах (диапазон `\u16A0-\u16FF` в лексере).
- Точность `Decimal` задаётся глобально через `getcontext().prec` (мутабельное глобальное состояние) — потенциальный источник багов при смешивании типов в одном выражении.
- Документация собирается через `mkdocs` (`mkdocs.yml`, `docs/`), есть VS Code синтаксис-плагин в `zmey-gorynich-syntax/`.
